本报告
本报告最重要的一条披露（计划书验收要求：TDC 报告必须明确通用加速卡的保护边界） 通用加速卡不是 GPU-TEE。本报告不宣称加速卡显存与 CPU—加速卡总线具备密码学机密性，也不表述为全链路密态。

还有一点必须讲清楚，否则极易被误读：当前这台机器上叠加运行着方案三的 OTP 盲化，所以实际下发到卡上的是 RNS 密文分量。但这是 FEC 机制带来的，不是 TDC 的性质。若按纯 TDC 形态运行（不启用 OTP），进入加速卡的将是明文激活。本报告按计划书"不以一套方案的证据替代另一套"的要求，不把这一条记为 TDC 的安全属性。

补充一项本轮取得的硬证据：该加速卡确实不具备机密计算能力——310P3 实测 work-mode、rootkey、tls-cert 均返回"不支持查询"，key-manage 服务 Stop，驱动与 CANN 中无 attest / confidential / cc_mode 符号。这不是把 TDC 说成 CDC 的余地问题，而是物理上就没有。

七、TDC-05　加速卡原生直通与独占使用

判定通过

直通与独占已由 vfio-pci 绑定 + 独立 IOMMU 组（每组 1 设备）+ device-share=False 确认，见上一节。

"其他租户无法读取残留数据"这一条本轮第一次做了真正的反向测试（此前完全空白）。做法：写进程在设备上分配 256 MB 填满唯一标记；另一个进程分配同样大小，不初始化直接读回。覆盖两种结束方式：

写进程结束方式
读进程结果
正常 aclrtFree 后退出
命中标记 0 次；非零字节 0 / 268,435,456
不释放直接退出（驱动回收）
命中标记 0 次；非零字节 0 / 268,435,456
读路径自检（阳性对照）
命中自己刚写入的标记 15,790,320 次 → 读路径有效

两轮读回的都是全零，而自检证明同一条读路径能看到刚写入的数据。结论：当前驱动下，后一个任务通过常规分配拿到的设备内存已被清零，读不到前一个任务的内容，异常退出场景同样成立。测试前后后端请求数不变。证据在 device_residue_02/。

限制：未做硬件复位级测试（如 FLR 前后的物理残留），仅覆盖驱动层常规分配路径。

九、TDC-07　边界外明文风险确认

判定软件侧已测，物理侧待补证

这一节是 TDC 报告的要害。计划书对本项的通过判定是"结论与实际观测一致，不将通用 GPU 误表述为 GPU-TEE 或全密态"——重点不在"证明没有明文"，而在如实记录能观测到的暴露面。

1　已经测到的

  • 设备内存侧：常规分配读不到他人内容（全零，见 TDC-05）。
  • 加速卡能力侧：310P3 实测不具备任何机密计算能力——work-mode、rootkey、tls-cert、tls-cert-period 均返回"不支持查询"，key-manage 服务 Stop，ecc-enable=True 属可靠性而非机密性，驱动与 CANN 中无 attest / confidential / cc_mode / secure_boot 符号（cdc01_platform/）。
2　必须写明的暴露面 纯 TDC 形态下，进入加速卡的是明文激活。当前这台机器因为叠加了方案三的 OTP 盲化，实际下发的是 RNS 密文分量；但那是 FEC 的性质，不是 TDC 的性质。如果客户按纯 TDC 方案部署（CPU-TEE + 通用加速卡直通，不启用 OTP），则：
· 激活值以明文形式经 PCIe 下发到卡；
· 卡上显存中存在明文激活与权重；
· 该卡没有显存加密、设备证明或链路加密能力（上方实测）。

因此 TDC 的安全性完全依赖于"卡被独占直通给这一个机密域，且宿主拿不到卡"这一隔离假设，而不是密码学保护。本轮对该假设做了反向验证（TDC-04/05），但隔离不等于加密——这正是计划书反复要求区分的两件事。
3　一处来源未定位的观测 guest 第 1 段内可检出 /opt/cvm（68 次）、serve35_cb（46 次）、python3（73 次）、ELF 头（16 次）等静态明文，合计 245 处 1 MiB 块命中；第 2、3 段为 0。
这些与本轮种植的任何标记都不重合（运行时标记与磁盘 I/O 标记在三段中均 0 命中）。曾假设它们来自 virtio 块设备共享缓冲，该假设已被磁盘标记对照证伪。倾向于是 guest 启动早期（机密内存生效前）或非机密页的残留，但来源尚未定位，现阶段只陈述观测，不武断归因。
4　尚未取得的证据 物理 PCIe 总线观测——无协议分析仪与探头。软件接口采样不等于总线抓包，本报告既没有做，也不声称做过。这一条按计划书记为待补证。
