一、一句话结论

已达成

完整的大模型推理已经真正运行在独立的 Guest 虚拟机内部，并且打通了 「客户端加密 → 信道只走密文 → Guest 内解密 → Guest 内推理 → 加密回传 → 客户端解密」 的端到端密态链路。宿主在通信信道上抓不到任何明文，加解密开销仅占端到端时延的 0.002%。

未达成（已定位到确切原因）

海光 CSV 内存加密没有启用。因此在实测中，拥有 root 权限的宿主管理员 仍然可以从 QEMU 进程内存里直接捞到明文 prompt（本报告 F2 项实测命中）。 根因不是代码问题，而是宿主内核缺少一个启动参数 —— 详见第七节。这一项必须如实告知， 不能因为传输层加密做好了就宣称「宿主看不到明文」。

关于加密开销的结论

六个用例的加解密总开销稳定在 0.15–0.25 毫秒，平均 0.185 ms， 占端到端时延的 0.0021%。也就是说，在这套方案里做端到端加密几乎不花钱， 性能瓶颈完全在 CPU 推理本身，不在密码学。这条结论对后续换更大模型、换更强机型同样成立， 因为加密开销只与消息长度有关，与模型规模无关。

必须明确的表述边界

基于本次实测，对外可以说的是：「在通信信道上宿主只能看到密文，会话私钥不出 Guest」。 不能说「宿主无法获取明文」或「宿主看不到模型」—— A8 与 A9 两项实测证明， 在 CSV 未启用的当前状态下，具有 root 权限的宿主管理员既能从内存捞到明文，也能从镜像提取模型权重。

七、CSV 内存加密受阻分析

7.1 已经确认具备的条件

条件状态实测依据
CPU 支持 CSV具备 /proc/cpuinfo 含 csv 标志；CPUID 0x8000001F 显示 SME=1 SEV=1 SEV-ES=1
C-bit 参数已确定 CBITPOS=47，物理地址位缩减=3（注意不是常见的 5）
PSP 安全处理器在线 ccp 0000:12:00.4: CSV API:1.5 build:2446；平台状态 = INIT
内核 KVM 支持已启用 kvm_amd: CSV enabled (ASIDs 1-500)、CSV2 enabled、CSV3 enabled
QEMU CSV 代码已具备 升级到 8.2.0-56 后二进制含 csv3_init、csv3_launch_encrypt_data 等完整海光 CSV3 符号
UEFI 固件已安装 edk2-ovmf-202308-32，含 ovmf.amdsev/OVMF.fd
CSV3 安全内存预留缺失 /sys/kernel/mm/csv3_cma/mem_info 显示 total cma size: 0 MiB

7.2 根因

宿主内核在开机第 0.02 秒就打出了这条日志：

[    0.021738] CSV: Fail, either kernel param csv_mem_percentage or
               csv_smcr_size&csv_use_hugetlb is required
[    0.021739] CSV: Don't reserve any memory
[    3.412253] ccp 0000:12:00.4: CSV3: fail to set secure memory region,
               CSV3 support unavailable

而当前宿主的内核命令行是：

BOOT_IMAGE=/vmlinuz-6.6.0-euler root=/dev/mapper/openeuler-root ro
rd.lvm.lv=openeuler/root cgroup_disable=files apparmor=0 crashkernel=512M rhgb quiet

里面没有任何 csv 相关参数。CSV3 需要在启动阶段从物理内存中划出一块连续的安全内存区 （CMA），这块区域必须在内核启动时预留，运行时无法补救。没有预留，PSP 就拒绝建立加密上下文， 表现为 QEMU 侧的：

qemu-kvm: sev_launch_start: LAUNCH_START ret=1 fw_error=21 'Feature not supported'
qemu-kvm: sev_kvm_init: failed to create encryption context

为排除是参数写法问题，已穷举验证 8 组组合（policy 取 0x0/0x1/0x20/0x21， 带与不带 user-id），以及 q35 与 pc 两种机型，错误码完全一致。 libvirt 的权威能力查询同样返回 <sev supported='no'/>。因此可以确定 不是调用方式问题，而是平台侧未就绪。

7.3 修复路径

需要一次宿主机重启，步骤如下（本次未执行，按用户决定保持机器状态不变）：

  1. 备份 /etc/default/grub；
  2. 在 GRUB_CMDLINE_LINUX 追加 csv_mem_percentage=50 （按需调整比例，代表划给 CSV3 的物理内存百分比）；
  3. grub2-mkconfig -o /boot/grub2/grub.cfg，建议用一次性启动项以便失败回退；
  4. 重启后确认 /sys/kernel/mm/csv3_cma/mem_info 的 total cma size 不再是 0， 且 dmesg 不再出现 CSV3 support unavailable；
  5. 以 -object sev-guest,id=sev0,cbitpos=47,reduced-phys-bits=3,policy=0x1 重试启动，验证 Guest 内核打印内存加密激活信息；
  6. 重跑本报告第六节的取证，预期 A8 由「暴露」转为「未命中」，届时安全闭环完整。

八、实施过程中解决的关键问题

这一节记录排障过程，供后续在同类机器上复现时少走弯路。

问题表象根因与解法
宿主「没有外网」 dnf 全部失败，Could not resolve host；此前被判断为机器不通外网， 只能从本地上传大文件 并非没网。IP 层完全通（ping 223.5.5.5 往返 15 ms）， 只是 /etc/resolv.conf 是指向 /run/systemd/resolve/ 的悬空符号链接， 而 systemd-resolved 未启用，导致 DNS 完全不可用。删除悬空链接并写入常规 nameserver 后， openEuler 源、PyPI、hf-mirror 全部恢复。此后所有依赖改为机器自行下载
PyTorch 装不上 先后试了 Windows 版（含 c10.dll）、PyPI 的 CUDA 版 （缺 libcudart.so.12），均无法在 Guest 运行 DNS 修好后直接在目标 rootfs 内 pip install --index-url .../whl/cpu torch， 装到原生 Linux CPU 版 torch 2.14.0+cpu，一步到位
模型加载失败 SafetensorError: incomplete metadata, file not fully covered 宿主上那份 model.safetensors 是 1,645,238,848 字节的损坏文件 （正确为 988,097,824 字节）。重新下载并用 safetensors 头部做完整性校验 （校验逻辑：8 字节头长 + 头 + 最大张量结束偏移 == 文件大小），确认 290 张量全覆盖后再写入镜像
Guest 起不来 用宿主 initramfs 直接引导，找不到根设备 宿主 initramfs 是 hostonly 模式，只含宿主 LVM 驱动。改用 dracut --no-hostonly --add-drivers "virtio_blk virtio_pci virtio_console ext4" 生成通用 initramfs
QEMU 读不到内核文件 dracut 生成的 initramfs 权限为 0600 root QEMU 以普通用户运行（用户已在 kvm 组，这样 unix socket 属主正确、 客户端才连得上），因此需要把内核与 initramfs 改为 0644
CSV 参数报错 Parameter 'reduced-phys-bits' is missing， 且 -object sev-guest,help 并未列出该参数 help 输出不完整。实际必填，且本机正确值是 3 而非常见的 5 —— 该值须从 CPUID 0x8000001F 的 EBX[11:6] 读取，不能照抄 AMD EPYC 的经验值
脚本把密码写进配置文件 /etc/resolv.conf 内容变成了密码字符串 sudo -S 从标准输入读密码，与 heredoc / 管道传数据互相抢占 stdin。 凡是需要写入内容的提权操作，一律先写临时文件再 sudo cp

9.2 通信协议

信道采用 NDJSON（一行一个 JSON 对象），共三类消息。这也是后续接入尤旺团队标准 prompt 接口时需要对齐的部分 —— 只需在客户端一侧做协议转换，Guest 内服务无需改动。

握手：
  客户端 → Guest   {"type":"hello"}
  Guest → 客户端   {"type":"pubkey","pub":"<base64 X25519 公钥>","model":"<名称>"}

推理：
  客户端 → Guest   {"type":"req",
                    "epk":"<base64 客户端临时公钥>",
                    "nonce":"<base64 12 字节>",
                    "ct":"<base64 AES-256-GCM 密文>"}
  Guest → 客户端   {"type":"resp",
                    "nonce":"<base64>",
                    "ct":"<base64>",
                    "stats":{"prompt_tokens":38,"gen_tokens":62,"latency_s":8.97}}

保活：
  客户端 → Guest   {"type":"ping"}   →   {"type":"pong"}

密钥派生方式：双方各自用 X25519 做 ECDH 得到共享密钥，再经 HKDF-SHA256(info="tdc-module2-session-v1") 派生 32 字节 AES-256-GCM 密钥。 Guest 侧私钥在进程启动时生成于内存，不落盘、不传输。

十、后续建议
