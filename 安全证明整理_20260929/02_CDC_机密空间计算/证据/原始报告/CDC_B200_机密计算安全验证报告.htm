CDC 机密计算安全验证报告
Intel TDX 机密虚拟机 + NVIDIA B200 CC 模式

验证日期 2026-09-23 ~ 09-24 · 宿主 gpuhost（Xeon 8568Y+ 192核 / 1885 GB / 8×B200）· 对应三方案中的方案二「机密空间计算」

一、一句话结论

已验证通过（核心安全主张成立）

在 b200 机器上把 CC 模式的 B200 整卡透传进 Intel TDX 机密虚拟机， CPU 内存加密（TDX）与 GPU 显存加密（Protected Memory）同时激活， GPU 远程证明（NVIDIA NRAS）全链路通过。核心安全实验——宿主以 root 权限全量扫描 QEMU 进程 16.66 GB 内存寻找 Guest 私有内存中的明文标记—— 0 命中（同期正控制 24105 命中，方法有效性已证）。

必须如实披露的边界（不是缺陷，是机密计算的固有属性 + 环境缺口）

  1. I/O 路径宿主可见：实测捕获到 Guest 内 sudo 审计日志行 （含测试命令明文）出现在 virtio-blk 的共享 DMA 缓冲中。凡是 Guest 主动写入模拟设备 （磁盘、网络）的数据，宿主都能看到——这是 TDX 的设计内行为，不是破解。 保护这类数据靠的是传输层加密（如端到端加密信道），与内存加密互补。
  2. CPU 侧 Quote 签名未打通：TDREPORT 接口已通 （/dev/tdx_guest + configfs-tsm provider=tdx_guest）， 但宿主未部署 QGS（Quote 生成服务），TD Quote 读出 0 字节。GPU 侧证明不受影响。
  3. 本报告为安全验证，性能数据（CC 模式下 matmul 1607 TFLOPS 等）仅作参考附于第七节。

二、验证了什么：CDC 与本实验的关系

三方案中 CDC（机密空间计算）的安全主张是：CPU 与 GPU 都处于硬件 TEE 中， 内存与显存都加密，两者之间的链路受保护，且能被远程证明。与之对照， TDC 只保证 CPU 侧隔离（GPU 明文可见），FEC 不要求 GPU 可信（卡上算密态数据）。

b200 机器正好补上了此前缺失的 GPU-CC 硬件（此前在昇腾 310P3 上核查为 「平台不具备能力」）。本报告逐项覆盖 CDC-01 ~ CDC-06：

编号安全任务 结论关键证据
CDC-01平台具备 GPU-CC 与 CPU-TEE 具备 8×B200 GPU CC capabilities: CC Capable；Intel TDX BIOS 已启用 （virt/tdx: BIOS enabled: private KeyID range [32, 64)，PAMT 7.9 GB）； libvirt <launchSecurity><value>tdx</value>
CDC-02建立 CPU-TEE 与 GPU 同时在域内的机密 VM 已建立 QEMU tdx-guest 对象 + OVMF.inteltdx 引导 Ubuntu 24.04； GPU0 经 vfio-pci 透传（挂 pcie-root-port）；Guest 内核 tdx: Guest detected / Memory Encryption Features active: Intel TDX
CDC-03CPU/GPU 双远程证明 GPU 通过 / CPU 半通 GPU：NRAS Attestation Successful，28 项声明全 true（第五节）； CPU：TDREPORT 接口可用，Quote 签名缺宿主 QGS 服务
CDC-04内存与显存隔离 实测通过 双 canary 取证实验（第四节）：私有内存 0 命中；显存 Protected/Unprotected 状态翻转（第三节）
CDC-05异常闭锁（CC 关闭时拒绝机密负载） 实测 CUDA Error 802 system not yet initialized：GPU Ready State 未置位时 CUDA 上下文无法建立——机密负载在 CC 未就绪时确实被挡
CDC-06数据路径关联与独立结论 本报告 以带正控制的双 canary 实验区分「私有内存受保护」与「I/O 共享路径可见」两类事实

四、核心实验：双 canary 内存取证

4.1 实验设计（方法学重点）

「宿主扫不到明文」这个结论要成立，必须同时排除两个相反的谬误：标记根本没放进去 （假阴性）和扫描方法本身无效（假保护）。因此设计三重保障：

  1. Guest 自扫：扫描前先在 Guest 内部扫一遍，确认标记真实驻留 （自扫 needle 从 /dev/shm 读取，不进命令行、不出 Guest）。自扫 0 命中则实验作废。
  2. 正控制：宿主上另起一个持有相同标记的普通进程。扫描器必须能在它里面 命中，才证明方法有效。
  3. 进程类型过滤：按 /proc/pid/comm 过滤目标必须是 qemu、 控制必须是 python——排除执行脚本自身的 shell（其命令行同时含标记与目标特征，曾污染判读）。

4.2 canary A（经 SSH 传入）：先给错再纠对的完整过程

第一轮用「宿主经 SSH 把 canary 传进 Guest」的方式放置，结果 QEMU 内存扫出 7~13 次命中。 没有直接下「EXPOSED」结论，而是用定位器查明每个命中落在哪段内存、 前后 96 字节是什么：

== MAP: 70527be00000-70567be00000 rw-p 00000000 00:00 0     ← guest RAM 后端大映射
   hits in region: 13
   asc: ...ot ; COMMAND=/usr/bin/python3 /tmp/selfscan.py
        CDC-CANARY-7f3a9e21b4c8d56f0a1e2d3c4b5a6978 cana

命中内容是 sudo 审计日志行——测试命令自身经 journald 落盘、 走 virtio-blk 的 DMA 共享缓冲留下的足迹。TDX 下 guest 私有页已从 QEMU 视图丢弃， QEMU 仍能读到的这段是 guest 主动置为 shared 的设备 DMA 页。 结论：泄漏渠道是 I/O 设备路径（设计内共享），不是私有内存失效。 7 次命中 vs Guest 内 24110 份副本，量级差三个数量级，也印证这是足迹而非驻留数据。

4.3 canary B（纯内存，定论实验）

排除一切 I/O 混淆：canary 在 Guest 内部用 os.urandom 生成， 明文从生成到消亡只存在于 Guest 私有内存——不进任何命令行（命令行经 SSH 传输）、 不写盘（needle 存 /dev/shm 即 tmpfs；宿主取 needle 走 SSH 加密信道，且只用于宿主侧检索参数， 宿主进程参数不会进入 QEMU 内存）。生成时仅打印其 sha256 供对账：

[2] Guest 自扫（有效性前提）

4.4 与海光 TDC 的对照（同一套方法学）

平台CPU 内存加密 宿主 root 扫 QEMU 内存找 Guest 明文
海光 TDC（CSV 未启用）无（fw_error=21） EXPOSED Guest 进程堆中的明文 prompt 直接命中 （16.6 GB 扫描、F2 项）
b200 CDC（TDX 激活）Intel TDX PROTECTED 纯内存 canary：Guest 内 24102 份 ↔ 宿主 16.66 GB 全扫 0 命中（正控制 24105 命中）

两平台用同一方法学（自扫 + 正控制 + 全量扫描）得到相反结论， 定量坐实了「内存加密开启与否」带来的安全差异——这正是 CDC 相对 TDC（不开 CSV 时）的核心价值主张。

五、GPU 远程证明（NRAS）结果

在 CVM 内通过 nv-attestation-sdk 向 NVIDIA NRAS （nras.attestation.nvidia.com）发起 GPU 远程证明，验证通过 （EAT token 3055 字节）。关键声明：

含义：数据方在向该 GPU 交付任何机密之前，可以独立验证 「对端确实是一块运行正版驱动与 VBIOS、未被篡改、处于 CC 模式的 B200」。 这是 CDC「交付前可验证」主张的实证。

CPU 侧：TDX 报告接口已通——/dev/tdx_guest 设备存在、 configfs-tsm provider: tdx_guest、inblob 可写。 但 TD Quote 读出 0 字节：Quote 签名需要宿主侧 QGS 服务 （Quote Generation Service），本机未部署。待补 部署 tdx-qgs + 配置企业根证书后即可补测 CPU 侧完整证明。

六、异常闭锁验证（CDC-05）

机密计算的闭锁语义是「保护没就绪就不干活」。实测：

# GPU Ready State 未置位时，在 CVM 内初始化 CUDA：
CUDA initialization: Unexpected error from cudaGetDeviceCount().
Error 802: system not yet initialized      ← CC 未就绪，拒绝建立 CUDA 上下文

# 置位 Ready（-srs 1，即属主确认证明流程后放行）后：
cuda available: True   name: NVIDIA B200   177.4GB   MATMUL_OK

即：CC 模式下 GPU 不接受跳过就绪流程的裸用法， 与「证明通过才允许机密负载」的设计一致。

七、附：CC 模式下的性能参考（非本报告重点）

matmul bf16 (8192³)      1607.17 TFLOPS     ← GPU 内部算力几乎满血
matmul fp16 (8192³)      1532.28 TFLOPS
D2D 显存拷贝             5805.96 GB/s       ← HBM 带宽无损
H2D (PCIe, 经加密弹跳缓冲)   9.25 GB/s       ← CC 代价集中在这里
D2H (PCIe, 经加密弹跳缓冲)  12.16 GB/s

机密计算的代价集中在跨 PCIe 传输（加密弹跳缓冲），GPU 内部计算与显存带宽基本无损。 对推理类负载（权重常驻显存、跨 PCIe 传输占比小）影响有限； 对频繁 H2D/D2H 的负载需把大块数据尽量留在显存内。

八、表述边界（对外材料请严格遵守）

不能说

  • 「宿主完全看不到任何数据」—— I/O 共享路径实测可见（sudo 审计足迹已定位）
  • 「CPU/GPU 双远程证明已全部完成」—— CPU 侧 Quote 因缺 QGS 未打通
  • 「全链路加密」—— PCIe 链路加密是 GPU CC 硬件行为，本实验未做物理总线观测， 不下物理层结论

可以说

  • 「Guest 私有内存中的明文，宿主以 root 全量扫描 16.66 GB 无法读到（0 命中， 正控制 24105 命中）」
  • 「GPU 显存处于全保护状态（Protected 177 GB / Unprotected 0）， CC 环境为 PRODUCTION」
  • 「GPU 远程证明通过 NVIDIA NRAS 全度量链验证（签名、证书链、nonce、度量值匹配）」
  • 「经模拟设备（磁盘/网络）的数据路径宿主可见，属设计内共享， 需由传输层加密保护」
  • 「CC 未就绪时 GPU 拒绝建立机密负载上下文（Error 802 实测）」

九、残余风险与待办

  1. 部署 QGS 补 CPU 侧 Quote（宿主装 tdx-qgs / sgx-dcap 兼容组件， 配置根证书），完成后 CDC-03 即完整。
  2. I/O 路径披露已在报告中如实呈现；如业务数据需走网络/磁盘， 沿用端到端加密信道（与 TDC 线同款 X25519+AES-GCM 方案）。
  3. 多卡 CC 域（Multi-GPU Mode）与 NVLink 在 CC 下的行为未测（本实验单卡）。
  4. 宿主重启后需重做：GPU vfio 绑定、dma_entry_limit 调大 （该参数重启回落为 65535）、CC 模式确认（GPU 侧 CC 设置持久于卡固件，但建议复查）。
