九、FEC-08　异常处理与安全回退（本轮新增故障注入）

判定条件通过多平台适配待补证

计划书对本项的通过判定是"各目标平台均保持密态边界，异常时中止任务而非回退到明文计算"。此前这一项只有"证明失败、随机源失败路径有测试覆盖"的间接说法，没有真正注入过故障。本轮补做了一套故障注入，结论分两半：能被发现的异常一律中止，但设备静默算错在批次路径上不会被发现。

测试方法与安全措施 独立进程运行，引擎源码拷贝出生产树后编译（被测源码 q8_ops.c 摘要 b6e0afa3…），不在 /data/otp_c35 原树内构建。没有用非法指针启动任何 kernel——NPU 与线上服务共享，三个非法形参用例都在触碰设备之前就返回。模拟"设备算错"的做法是：把设备上某一个输出通道的权重按位翻转，而可信侧的 host 权重副本保持不变，用例结束后立即还原并复验。
测试前后后端 requests 均为 28、active=0，引擎 healthz 仍为 {"status":"ok","mode":"shannon_rns_otp"}——生产服务未受影响。

要说清楚它是什么、不是什么：
· 不是机密性问题。无论哪条路径，设备拿到的始终是 OTP 密文分量，掩码与解盲都在 CVM 内——密态边界没有被破坏，这一点故障注入前后都成立。
· 是完整性问题。FEC 的威胁模型明确把加速卡列为不可信。一个故障的或被控制的加速卡，可以在批次推理中静默篡改输出而不被发现。
· 是有意的性能取舍，不是疏漏。源码注释写明：批次下这个额外点积"会抹掉部分批处理收益，而 RNS 精确重建本身仍然成立"。也就是说，作者认为交叉校验是防设备故障的，不是保证数值正确的。这个判断在"设备可信"的前提下成立，在"设备不可信"的前提下不成立。

建议（未实施，属代码改动需另行授权）：批次路径增加抽样校验（例如每批抽若干 [m,n] 做 CPU 点积对拍），在可接受开销下恢复完整性检测；同时把 corrected N mismatches 事件从 stderr 日志提升为显式上报，否则设备故障对调用方始终不可见。
通过的部分 能被发现的异常，一律中止而非降级。非法形参、不支持的配置、随机源失效三类都是 rc=-1 直接中止。其中随机源失效这一条对 OTP 尤其关键——它证明了拿不到熵时不会退而用弱随机或无掩码继续算，而是停下来；恢复供熵后正常运行。这与 FEC-07 的"运行时无法降级为明文"相互支持：既不能被外部请求降级，也不会因内部故障自行降级。

多平台适配（待补证）

仅昇腾 310P 实测。DCU、GPU、TPU 等平台未测，在未声明支持范围前不做判定。这也是对外材料中"全谱系适配"表述需要修订的依据。另外，加速卡硬件级故障注入（掉卡、ECC 错误、复位）与不支持算子的异常路径本轮未注入——前者需要可牺牲的硬件环境，后者需要先明确算子支持清单。
