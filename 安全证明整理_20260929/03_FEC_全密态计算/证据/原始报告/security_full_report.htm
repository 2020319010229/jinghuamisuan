三类密态计算安全测试 · 执行与结论

2026-09-18 · 依据《三类密态计算安全测试方案》与《荆华密算三类密态计算解决方案安全证明任务计划书》 · 鲲鹏 920 + virtCCA CVM + 双 Ascend 310P

本轮把方案规定的公共测试、方案一（TDC）与方案三（FEC）流程实际跑完。当前部署（鲲鹏 virtCCA 机密虚机 + 双 310P vfio 直通）正是计划书所述 TDC 的架构形态——CPU-TEE 加通用加速卡原生直通，因此 TDC-01 至 TDC-07 均在本机实测，包括此前未做的宿主侧内存读取、非授权侧访问与跨任务设备内存残留。

方案二 CDC 也做了实际核查而非推测：设备直接返回不支持 rootkey、tls-cert 与 work-mode 查询，key-manage 服务处于 Stop，据此判定为平台不具备 CDC 所需能力。

结论：FEC 通过（核心项全部实测通过）、TDC 条件通过（隔离与独占项通过，两处需继续定位）、CDC 平台不支持（有设备实证）。存在 1 项 HIGH 级既有风险（F01 明文推理路由）仍未整改，本报告如实保留。

三、方案一：可信空间计算（TDC）

宿主能否读到机密虚机的内存

这是 TDC 最核心的一条主张，此前只有平台配置证据（内核参数、tmm_driver、IOMMU 绑定），没有做过反向读取。本轮做了一次带对照的实测。

从 qemu 命令行确认 guest 内存由 3 个 44 GB 的 NUMA backend 组成（共 138 G）。首版扫描只覆盖了 4.5%，结论不成立；最终版把三段全部扫完：读取 130.39 GB / 候选 134.19 GB，覆盖率 97.16%，全程无 errno 错误。

检查结果含义
宿主扫宿主进程（阳性对照）命中搜索例程本身有效
CVM 内自搜运行时标记命中标记确实驻留在 guest 内存中
宿主扫 guest 找运行时标记0 次三段共 130 GB 读完仍未取得
宿主扫 guest 找磁盘 I/O 标记0 次经块设备写入并回读的数据同样未取得
guest 段内静态明文特征245 处，全部集中在第 1 段第 2、3 段（共 86 GB）零命中，连 ELF 头都没有
内存段大小已读静态明文种植标记
0xfff4a3e0000044.0 GB44.0 GB2450
0xffe9a3c0000044.0 GB44.0 GB00
0xffdea3a0000044.0 GB42.4 GB00

这个分布本身就是判据：若 guest 运行时内存对宿主是明文可见的，一台正在跑 35B 模型、占用 40 GB 以上内存的虚机，不可能有 86 GB 连一处可识别明文都没有。

需要如实记录的发现。第 1 段中可检出 /opt/cvm（68 次）、serve35_cb（46 次）、python3（73 次）、ELF 头（16 次）等静态明文，合计 245 处 1 MiB 块命中；另两段为 0。

这些与本轮种植的任何标记都不重合：运行时内存标记与磁盘 I/O 标记在三段中均为 0 命中。曾假设它们来自 virtio 块设备共享缓冲，该假设已被磁盘标记对照证伪。倾向于是 guest 启动早期（机密内存生效前）或非机密页的残留，但来源尚未定位，列为后续项，现阶段只陈述观测。

本项判定：通过（TDC-03），另记一条待定位观测（归入 TDC-07）。计划书对 TDC-03 的通过标准是"非授权侧不能取得业务明文、密钥或受保护内存内容"。在 97.16% 覆盖、两个阳性对照成立、两类标记各自独立种植的条件下，宿主侧未取得任何业务明文——该标准已满足。仍不能由此推广为"CVM 内存对宿主完全不可见"，第 1 段的 245 处静态明文就是反例，须在 TDC-07 中如实披露。

TDC-05 任务结束后的清理：跨进程设备内存残留

计划书要求"其他租户无法并发占用或读取残留数据"。做法是写进程在设备上分配 256 MB、填满唯一标记，然后由另一个进程分配同样大小并在不初始化的情况下读回。覆盖两种结束方式：正常释放，以及进程直接退出、由驱动回收。

写进程结束方式读进程命中标记读到的非零字节读路径自检
正常 aclrtFree 后退出00 / 268,435,456命中 15,790,320 次
不释放直接退出（驱动回收）00 / 268,435,456命中 15,790,320 次

两轮读到的都是全零，而自检证明同一条读路径能看到刚写入的数据。因此可以说：在当前驱动下，后一个任务通过常规分配拿到的设备内存已被清零，读不到前一个任务的内容；异常退出的场景同样成立。测试前后后端请求数不变、结束时空闲。

四、方案二：机密空间计算（CDC）

CDC-01 的任务本身是"核对平台组合、确认 GPU 是否处于正式机密计算模式"，这一步在本机可以做，本轮做了实际核查，不再以推测下结论。

判定：平台不支持，而非未测。CDC-03「GPU 可信状态与远程证明」要求设备身份与证明材料，310P3 明确不提供 rootkey 与 tls-cert；CDC-01 要求确认 GPU 处于正式机密计算模式，该设备连工作模式查询都不支持。CDC-04 组合可信链、CDC-05 显存隔离、CDC-06 链路加密、CDC-08 异常闭锁均以这两项为前提，因此在本硬件上不具备执行条件。

按计划书"三套方案分别形成独立安全结论，不以其中一套方案的证据替代另一套"的要求，本轮没有用 FEC 的密态证据或 TDC 的隔离证据去填充 CDC 结论。要完成 CDC，需要更换为具备 GPU-CC 能力的硬件平台。

多类型加速卡待补证仅昇腾 310P 实测，其他平台未声明范围前不判定

故障注入查实的一条缺口（本轮更正了此前的表述）。此前写的是"设备侧返回异常时存在由可信 CPU 补正并继续返回成功的分支"。故障注入加静态确认后，准确的说法是：verify = g_rns_verify && (M == 1 || getenv("OTP_RNS_DEBUG"))——与设备结果的 CPU 交叉校验只在单行路径开启，多行批次默认不做。实测：把设备上一个输出通道的权重按位翻转而保持可信侧 host 副本不变，M=1 时被检出并纠正（偏差回到 2.98e-05），M=4 时偏差 567.615 且按成功返回。

需要分清它是什么：不是机密性问题——两条路径下设备拿到的都是 OTP 密文分量，密态边界没有被破坏；是完整性问题——FEC 的威胁模型把加速卡列为不可信，而故障或被控制的加速卡可在批次推理中静默篡改输出。源码注释表明这是有意的性能取舍（批次下额外点积会抹掉部分批处理收益），该判断在"设备可信"前提下成立。建议批次路径增加抽样校验，并把 corrected N mismatches 从 stderr 日志提升为显式上报。相关改动属代码修改，未实施。

七、未覆盖与限制

  • CDC 全部专项：310P3 不提供设备证明材料与机密计算模式，需更换具备 GPU-CC 能力的硬件才能执行。
  • 物理 PCIe 总线观测：无协议分析仪与探头；软件接口采样不等于总线抓包。
  • 跨租户越权：单租户部署，无第二租户可越权；已改测宿主机与非特权用户两类非授权侧，不等同于完整多租户隔离证明。
  • Web 入口：本环境未部署 Web 前端，仅测 SDK。
  • F01 明文推理路由：HIGH 级，本轮复现仍存在，未整改。
  • guest 段内 245 处静态明文：来源未定位。
  • 第三方材料映射：经信局报告到三类方案的逐项映射未完成。
  • 本报告属于工程安全验证，不等同于形式化密码学证明或权威认证；所有结论限定于本次实际验证的环境与版本。
